## Defects found and retested

1. The #625 visibility regression allocated a fixed 2000 x 1600 canvas, but the
   production renderer on this host used 2357 x 1561 bounds. The original run had
   one out-of-bounds failure among 49 tests. Allocating the canvas from the actual
   renderer bounds fixed the test; the final 49 passed without skips. Floating
   editing and browsing now both cover pending markers, complete publication,
   replacement, cancellation, reentry and rejection of retired work. Production
   rendering was not changed to accommodate the test.
2. [Issue #627](https://github.com/wimi321/lizzieyzy-next/issues/627) exposed a real
   import-recovery bug: permanent snapshot preparation failures were retried in
   the background while the pending-import gate blocked Continue. The minimal
   regression failed in two of three cases before the fix. The coordinator now
   terminates that failure, retains the game, pauses analysis and reports the
   cause. Explicit Continue performs full rules/position synchronization again;
   stale readers, replaced engines, new games and comparison-engine failures
   remain fenced. The final focused selection passed 37/37. The safety selection
   had 120 records, zero failures/errors and one non-Windows-only skip.
3. The issue's `helper.bat` launcher still cannot prove that it can read local
   snapshot files. This is an intentional security boundary, not a capability
   granted by the fix. Direct local executable commands with equivalent GTP
   options remain supported; SSH, scripts and interpreters are still rejected
   before destructive board commands where exact restoration is not provable.
4. An existing `MoreEnginesDraftTest` fixture restored global configuration before
   its own `SwingWorker.done()` finished. A late refresh timer then accessed a
   later fixture's deliberately incomplete configuration. A controlled regression
   reproduced four failures in seven tests with the old cleanup order. The
   fixture now waits for its own worker, DONE event and EDT completion, stops its
   final timer, checks uncaught asynchronous errors, and only then restores global
   state. The related 61 tests passed without skips. Production still executes
   the same SwingWorker through a transparent package-private submission seam;
   no production null guard was added to conceal invalid fixture state.
5. The first combined native-focus CI failed although its child completed all
   scenarios, exited successfully and saved SGF `rootVisits=76`. The receipt
   reread the public live counter after a screenshot and observed the writer's
   intermediate `-1`. It now captures under the BoardData writer's monitor and
   records the same positive value it actually asserts. Real engine capability,
   visits, SGF root/edge allocations, screenshots and cleanup remain required.
   The repaired [native Windows run](https://github.com/wimi321/lizzieyzy-next/actions/runs/39044302966)
   passed. This was an acceptance-receipt race, not evidence of an engine restart.

## Remaining product and input gates

The native Windows desktop selection executed 30 cases: 28 passed, two physical
input chains failed waiting for the toolbar search. Geometry showed a visible,
unclipped button and correct Swing hit target, but Robot movement left the pointer
fixed and no press/release reached the JVM. Binding the single target device did
not change that. This does not establish a product-button defect, nor is it a
pass: Windows input delivery on this host remains unverified. No synthetic
`doClick`, longer timeout, physical DPI change or security change replaced it.

Direct computer-use interaction was unavailable because the required node_repl
tool was not exposed. Human verification of startup, clipboard setup positions,
pause/continue, previews and saving/reopening was requested. No manual input,
screen-reader speech, every audio output device or locked/remote desktop behavior
is claimed as passed.

Source checks and simulated product fixtures do not validate a final release
archive. Before public publication/stable promotion, consume the exact final
Windows assets and their producer provenance, verify launcher/runtime/JAR/engine
closure identity, run the applicable product scenarios and retain cleanup
evidence. Preserve any unmet native-input or product prerequisites as BLOCKED;
never manufacture acceptance records. Artifact-specific receipts and publication
decisions belong with PR #628 and the release workflow, not with an assumed
universal PASS here.

No real Zhizi, ChatGPT, Fox login/account, payment flow, native AMD/Intel GPU,
TensorRT, ROCm, DirectML, OpenVINO or Metal acceptance is claimed by this host
record. Experimental functionality remains experimental.
