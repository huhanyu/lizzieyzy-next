## Defect found and fixed before release

The first engine build with the #662 patch (run 39581395252) was timed in analysis mode before
staging, and the app's whole-game quick analysis turned out about 30 times slower:

- The patch padded every GPU batch to `nnMaxBatchSize`, including a size set in the config.
- The bundled `analysis.cfg` is KataGo's `analysis_example.cfg`, which sets 64. Automatic quick
  analysis runs it with two search threads and 2 visits per position (the command in `app.log`:
  `-override-config analysisPVLen=15,numSearchThreads=,numSearchThreadsPerAnalysisThread=1`).
- Every batch of one or two positions therefore ran 64 rows.

#664 pads only when KataGo derives the batch size (no `nnMaxBatchSize` in the config, as with the
bundled `gtp.cfg`). The same fix is in the upstream proposal, lightvector/KataGo#1270. The #662
engine was never published.

Quick analysis of the first 80 positions of the ear-reddening game, sent as `katago analysis`
queries the way `AnalysisEngine` sends them:

| Engine | All 80 positions | First result |
|---|---|---|
| `next-2026-10-17.1` engine (upstream) | 6.8 s | 2.9 s |
| #662 engine | 216.9 s | 6.7 s |
| #662 engine with `metalPadBatch = false` | 6.8 s | 2.9 s |
| Release engine (#664) | 6.8 s | 2.9 s |

## macOS engine (#662, #664)

KataGo's Metal backend runs MPSGraph at whatever batch size the search produces, and MPSGraph
compiles a new executable, about 3 s for B11 on the M4 Pro, the first time it sees each size.
Restarting analysis makes the next batches small, so an engine session froze several times in its
first minutes. `sample` during a freeze showed the `MPSGraphExecutable_queue` thread in
`mlir::collectRegions` while every search thread waited in `NNEvaluator::evaluate`.

When KataGo sizes the batch itself, the patched backend uses KataGo's existing fixed-shape batch
policy and pads GPU batches to `nnMaxBatchSize`, which then defaults to about half of
`numSearchThreads`.

GTP, one engine start and 24 analysis restarts on move 127 of the same game, alternating ordinary
and `focus` analysis, bundled 6-thread setting (freezes counted over the restarts):

| Engine | Freezes | First visits after start | Visits/s, ordinary / focus |
|---|---|---|---|
| `next-2026-10-17.1` engine | 2 | 5.8 s | 53 / 27 |
| Release engine (#664) | 0 | 3.2 s | 53 / 27 |

The development measurements in `docs/KATAGO_SOURCE_BUILD.md` (6 and 8 threads,
`metalPadBatch = false`, padding to 8 rows) used the older B11 snapshot bundled with the September
app (`b11c768h12nbt3tflrs`, SHA-256 `1881600c…`) and show the same pattern.

Release engines:

- arm64: build, packaging and dependency audit pass. The engine reports
  `Git revision: 47aadc08518b3e121f22539796c911002f699584-dirty` and records the patch. On the M4 Pro:
  - `testbackendreference` passes; its error statistics match the `next-2026-10-17.1` engine to
    within 0.00003;
  - the real-hardware focus probe (`probe_katago_focus.py`) passes and is the archive's acceptance
    evidence;
  - the restart and quick-analysis results above.
- x86_64: build, packaging and dependency audit pass, with the same revision and patch record.
  Under Rosetta 2 on the M4 Pro, which uses Apple's GPU and is not Intel hardware, it passes the
  focus probe, has no freeze in the 24 GTP restarts (52 visits/s), and runs the 80-position quick
  analysis in 11.7 s (the first result after 7.8 s; compiling is slower under translation). GPU inference was not run on Intel hardware, so acceptance stays `PENDING_HARDWARE`, as
  for the previous Intel archive.

## Application

- Every merged pull request passed CI: repository checks, Linux and Windows Java tests, the Linux
  desktop smoke test, Linux and Windows engine-process tests, and the Windows layout checks where
  they apply. Flakes that passed on rerun are recorded in the PR threads (#659, #663 Windows engine
  process; #662 desktop smoke); none touched changed code.
- The main window, right-click menu and 「评估此点」 changes were checked in the real macOS app with
  before/after captures (light and Apple styles, the maintainer's 1900 x 963 window).
- 「评估此点」 was exercised end to end with the patched engine. A point added during the
  whole-game analysis keeps growing after the analysis ends. While paused, the item is disabled with
  the label 「评估此点（分析已暂停）」 and a hint to press Space, and adding a point directly is refused.
  With official KataGo 1.16.5 the item reads 「评估此点（需新版引擎）」.
